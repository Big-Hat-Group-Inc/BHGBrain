## 2. Executive summary

The engineering discipline here is visible everywhere: circuit breakers, a storage lifecycle lock, `vector_synced` tombstones, bounded and resumable reconciliation, an archived design proposal behind nearly every subsystem. Almost none of the defects below are gaps in one of those mechanisms — they are seams *between* them, where two individually correct designs were composed without being tested against each other.

Three risks dominate. First, the retention garbage collector takes a lifecycle lock that rejects every write it then makes, so expiry, archival, audit-log and revision pruning have never run — while `/health` reports retention healthy and both history tables grow past their configured caps. Second, both delete paths remove the Qdrant vector before the SQLite row and leave the SQLite step outside the compensation, so one in-process failure yields permanent divergence that no health component, log or metric can see. Third, the Qdrant client carries the library's 300-second default timeout, most call sites bypass the breaker, and the unauthenticated `/health` endpoint runs that probe uncached on every request while answering 200 with the vector store down.

**Counts** — Critical 2 · High 18 · Medium 47 · Low 29 · Info 1 (97 findings).

## 5. Detailed findings

### Reliability

#### [Critical · High · S] `deleteMemory` removes the Qdrant vector before the SQLite row — `src/storage/index.ts:295-308`

**Issue:** `deleteMemory` awaits `qdrant.delete` (line 299) and only then calls `this.sqlite.deleteMemory(id)` (line 303). The SQLite step is outside any try/catch, and `SqliteStore.deleteMemory` opens with `assertMutableAllowed()` (`sqlite.ts:1046`, guard at `2485-2489`), which throws whenever a lifecycle operation is held. Nothing marks the row or logs on that path. `writeMemory`'s Qdrant-failure branch has the same shape: `markVectorSync(stamped.id, false)` at `index.ts:154` is also guarded and can throw.

**Failure scenario:** A user calls `forget` (`tools/index.ts:355`). `qdrant.delete` succeeds and the promise yields. During that yield `RetentionService.runGc` takes `beginLifecycleOperation('gc')` (`retention.ts:111`) and holds it across its own awaits (`retention.ts:152`, `196`) — a multi-second window, not a microsecond one. The resumed `sqlite.deleteMemory` throws `Storage lifecycle operation in progress: gc`. The vector is gone from Qdrant forever; the SQLite row survives with `vector_synced = 1`. The same window is opened, and much wider, by `BackupService.restore` (`backup/index.ts:203`), which holds the lock across a full Qdrant scroll.

**Why it matters:** The memory keeps appearing in `recall`, `memory://list` and fulltext while semantic search can never surface it again. A user who retries heals it; a batch `forget`, an agent that gives up, or `consolidate`'s source cleanup (`tools/index.ts:945`) does not.

**Recommendation:** Delete the SQLite row first (or set `vector_synced = false` before the Qdrant call), and route the SQLite step through a try/catch that marks the row unsynced and logs a structured cross-store event — mirroring `deleteCollectionData` (`storage/index.ts:370-388`). Pass `allowDuringLifecycle` on the compensating write, which `markVectorSync` already supports (`sqlite.ts:1660-1666`). Best combined with a pre-flight lock check so nothing is destroyed while a lifecycle operation is held.

**Divergence:** SILENT. `vector_synced` stays true, so `countUnsyncedVectors()` returns 0, `HealthService.checkVectorReconciliation` reports healthy, and `check()` performs no SQLite-vs-Qdrant point-count comparison anywhere. No metric, no log on the failing path — only `handleTool`'s generic `tool_error` line.

#### [Critical · High · S] `deleteMemories`' SQLite delete sits outside the compensation — `src/storage/index.ts:333-353`

**Issue:** Only `qdrant.deleteMany` is wrapped (334-342), and the compensating `markVectorsSyncBatch(ids, false)` lives in that Qdrant-only catch (341). `this.sqlite.deleteMemoriesByIds(confirmedIds)` at line 349 is outside any try: if it throws after the vectors were removed, the exception propagates and the rows stay with `vector_synced = 1`.

**Failure scenario:** With `retention.archive_before_delete: false`, `runGc` calls `deleteMemories` inside its own `gc` lifecycle bracket (`retention.ts:152`). `deleteMany` succeeds for group 1 — those vectors are gone — and `deleteMemoriesByIds` then throws the lifecycle error deterministically (`sqlite.ts:1071`). Retention's inner catch (`retention.ts:153-156`) synthesises `{deleted: 0, unreconciled: all, degraded: true}`, but the `vector_synced` flag was never actually cleared. The same shape occurs for any SQLite-side failure (SQLITE_FULL, SQLITE_BUSY per F5) after a confirmed vector delete.

**Why it matters:** The comment at `index.ts:326-331` states the guarantee this path is meant to provide — "their `vector_synced` flag is explicitly cleared so they remain visible as cross-store drift". That guarantee holds for a Qdrant-side failure and not for a SQLite-side one, which is the direction that actually loses data.

**Recommendation:** Wrap `deleteMemoriesByIds` and, on failure, mark the confirmed-but-undeleted ids `vector_synced = false` (with `allowDuringLifecycle`), return them in `unreconciled` with `degraded: true` rather than throwing. Alternatively invert the order so an orphaned *vector* — detectable and harmless — is the worst case.

**Divergence:** SILENT. `vector_synced` stays 1, `countUnsyncedVectors()` returns 0, `vector_reconciliation` reports healthy, and the returned `unreconciled` list contradicts what the database actually records.

**Deliberate:** `2026-08-30-batch-retention-and-vector-cleanup` — its spec explicitly promises this behaviour for the Qdrant-failure half; the SQLite-failure half was never covered.

#### [High · High · M] Retention GC holds a lifecycle lock that rejects every write it makes — `src/backup/retention.ts:111`

**Issue:** `runGc` calls `beginLifecycleOperation('gc')` (line 111) and then performs all of its mutations inside that bracket. Every mutating `SqliteStore` method begins with `assertMutableAllowed()` (`sqlite.ts:2485-2489`), which throws whenever `lifecycleOperation` is set: `archiveMemory` (`1808-1809`), `deleteMemoriesByIds` (`1070-1071`), `insertAudit` (`2155`), `pruneAuditLog` (`2110`), `pruneRevisions` (`2129`) and `setRetentionDegraded` (`1616`). The outer catch (`retention.ts:233-239`) calls `setRetentionDegraded` *before* the `finally` releases the lock, so it throws too and replaces the real error. Reproduced end to end against a real `SqliteStore`: every `archiveMemory` logs `retention_gc_archive_failed: Storage lifecycle operation in progress: gc`, `runGc` then rejects, the memory is still present, and `retention_state` is left `{degraded: false, last_success_at: null}`.

**Failure scenario:** Default config (`scheduled_cleanup_enabled: true`, `cleanup_schedule: '0 2 * * *'`). At 02:00 the `CleanupScheduler` tick calls `runGc`, which rejects; the scheduler logs one `retention_scheduler_run_failed` line and reschedules. Even with zero expired memories the run still fails, because `pruneAuditLog` (`retention.ts:183`) runs unconditionally. Forever after: nothing archived, nothing deleted, no compaction, `audit_log` and `memory_revisions` growing past their configured caps (50,000 / 20), and `HealthService.checkRetention` reading `degraded: false` with `cleanup_lag_seconds: null` — documented as "unknown", not "broken". `bhgbrain gc` fails identically.

**Why it matters:** The entire tiered-retention feature is a no-op in production while both the health endpoint and the docs say it works. Storage grows without bound in both stores and expired data is retained indefinitely, which is a data-retention-policy problem as much as a bug. Several other findings (F21, F23, F76) are latent behind it and arm the moment it is fixed.

**Recommendation:** Thread the `allowDuringLifecycle` option that `markVectorSync`/`markVectorsSyncBatch` already have (`sqlite.ts:1443-1478`) through `archiveMemory`, `deleteMemoriesByIds` (via `StorageManager.deleteMemories`), `insertAudit` (via `logAudit`), `pruneAuditLog`, `pruneRevisions` and `setRetentionDegraded`, and pass it from `runGc` — this is option two of the archived task 4.1, which the implementation skipped. Move `setRetentionDegraded` in the outer catch after the lock is released. Then replace the mocked-`sqlite` GC tests with at least one real-store integration test (see F65).

**Divergence:** Not a store divergence — both stores retain the data equally. SILENT to health and metrics; the only signal is one `retention_scheduler_run_failed` line per night. `src/backup/retention.test.ts:546-553` already documents the mechanism verbatim as "a separate, pre-existing behavior outside this change's scope".

#### [High · High · M] Four SQLite mutators issue multiple statements with no transaction — `src/storage/sqlite.ts:805-861, 1000-1043, 1045-1056, 2073-2090`

**Issue:** `insertMemory` (INSERT `memories`, then INSERT `memories_fts`), `updateMemory` (UPDATE, DELETE fts, re-INSERT fts), `deleteMemory` (three DELETEs) and `deleteMemoriesInCollection` (DELETE fts then DELETE `memories`) each run their statements in autocommit mode, so each is its own transaction. The transactional counterparts sit next to them: `hydrateBatch` (`889-914`), `insertMemoryFromPayloadAtomic` (`927-998`, SAVEPOINT), `deleteMemoriesByIds` (`1070-1091`) and `migrateToFts5` (`680-697`). `deleteMemoriesInCollection` additionally omits the `memory_links` cascade that both other delete paths perform (`1053`, `1083`), against `deleteMemoriesByIds`' own comment claiming bulk deletes never leave dangling edges.

**Failure scenario:** A `remember` updates an existing memory. `updateMemory` commits the UPDATE, commits the `DELETE FROM memories_fts`, and the re-INSERT fails (SQLITE_BUSY per F5, or SQLITE_FULL). The memory now has its new content in `memories` and no row in `memories_fts` at all: permanently invisible to `search` in fulltext or hybrid mode while `recall`, `memory://{id}` and semantic search still return it. Nothing rebuilds it — `ensureFtsSchema` (`630-660`) returns early once `memories_fts` is already FTS5, so `backfillFtsFromMemories` never runs. Symmetrically, `deleteMemoriesInCollection` failing on its second statement — called from `deleteCollectionData` (`storage/index.ts:389`) *after* `qdrant.deleteCollection` already succeeded — leaves every memory in the collection present in SQLite at `vector_synced = 1` with no vector.

**Why it matters:** A memory silently dropping out of fulltext is undetectable by any health component (`checkVectorReconciliation` keys only on `vector_synced`) and unrecoverable without hand-rebuilding the FTS table. The `deleteCollectionData` variant is a permanent silent cross-store divergence on a documented user operation, and the missing link cascade surfaces directly through `relate { action: 'list' }`, which returns raw rows without resolving `to_id`.

**Recommendation:** Wrap each of the four in `BEGIN`/`COMMIT` — or `SAVEPOINT`, so they compose inside `deleteMemoriesByIds`-style outer transactions — using the shape already proven in `hydrateBatch` and `insertMemoryFromPayloadAtomic`. Add the `memory_links` cascade to `deleteMemoriesInCollection` and delete `memories` before `memories_fts` under one transaction. Better still, funnel all three delete paths through one helper so the invariant lives in one place.

**Divergence:** SILENT for the memories-row-without-FTS-row case (no `vector_synced` change, no log, no metric, and nothing compares `countMemories()` against the FTS row count) and SILENT for the `deleteCollectionData` variant, since `markVectorsSyncBatch(ids, false)` runs only on the Qdrant-failure branch.

#### [High · High · S] No `PRAGMA busy_timeout`, on a single-writer premise the code's own docs contradict — `src/storage/sqlite.ts:525-546`

**Issue:** `openDatabase` sets `journal_mode = WAL` and `synchronous = NORMAL` (lines 538-539) and never sets `busy_timeout`, so SQLite's default of 0 applies: lock contention returns SQLITE_BUSY immediately with no wait. Nothing in `src/` handles SQLITE_BUSY. The rationale comment at `422-436` justifies this with "every read/write goes through this one `DatabaseSync` instance in this one Node.js process" — false in two shipped configurations: `README.md:835-843` documents spawn-per-client stdio as fully supported, and `src/cli/index.ts:25-31` opens its own store on the same `data_dir` for every `bhgbrain gc`/`repair`/`backup`.

**Failure scenario:** An operator runs `bhgbrain repair --from-qdrant` (whose `hydrateBatch` holds the write lock for a whole collection) while the server is serving `remember`. Verified on this machine (Node 22.23.2): with connection A in `BEGIN IMMEDIATE`, connection B's INSERT fails after 0 ms with `database is locked`. The server's `insertMemory` throws, `StorageManager.writeMemory` wraps it as `INTERNAL`, and the client's memory is simply not stored — or, mid-`updateMemory`, produces exactly the fulltext-invisible memory in F4. A 5 s busy timeout would have waited and succeeded.

**Why it matters:** This is the trigger that turns F1, F2, F4 and F6 from theoretical into routine, and it makes ordinary CLI use fail with a raw lock error instead of waiting.

**Recommendation:** Add `PRAGMA busy_timeout = <n>` in `openDatabase` alongside the WAL pragmas (config-backed, a few seconds), map a residual busy error to a retryable `BrainError` in `StorageManager`, and correct the rationale comment at `422-436`.

**Deliberate:** `2026-08-30-migrate-sqlite-to-native-engine` (design.md:42-43 lists "No multi-process access to brain.db" as a non-goal) and `add-operations-security-reliability` (lock retry de-scoped). Both rationales were written against sql.js's in-memory image and were not revisited when the store moved to a real on-disk file with a separate CLI entry point.

#### [High · High · M] `updateMemory`'s compensation is itself guarded and leaves phantom history — `src/storage/index.ts:202-239`

**Issue:** For a T0 memory whose content changes, `insertRevision` and a `REVISE` audit entry are written at lines 202-216, *before* `sqlite.updateMemory` (218) and the Qdrant upsert (222). The compensation block (234-238) replays only `rollbackFields` — it does not delete the revision row or the audit entry — and is itself unguarded: both `sqlite.updateMemory` (`sqlite.ts:1001`) and `markVectorSync` (`1651`) call `assertMutableAllowed()`.

**Failure scenario:** (a) A T0 update while Qdrant is down writes a revision identical to the restored content plus an audit entry for a revision that never happened; an agent retrying for twenty minutes adds one phantom revision per attempt, and at the default `revisions_per_memory_max: 20` that evicts the memory's entire real history. (b) The same update while a GC or restore holds the lifecycle lock: the rollback at line 235 throws `Storage lifecycle operation in progress`, which replaces the real Qdrant error, and `markVectorSync(id, false)` at 236 never runs. SQLite keeps the *new* content, Qdrant keeps the *old* vector, `vector_synced` stays 1 — semantic search retrieves the memory on the old content's embedding and returns the new text.

**Why it matters:** (b) is a silent permanent divergence producing wrong search results, with an error message that blames the wrong subsystem. (a) corrupts the append-only revision history that the `revisions` tool and `revertMemory` both depend on.

**Recommendation:** Defer `insertRevision` and the `REVISE` audit until after the Qdrant upsert is confirmed (or delete both in the compensation, capturing the revision number from line 204). Wrap the compensation in its own try/catch that logs a `compensation_failed` event and rethrows the *original* Qdrant error, and pass `allowDuringLifecycle: true` to the compensating writes.

**Divergence:** SILENT for case (b) — `vector_synced` left true, nothing logged from the compensation path at all. Case (a) is single-store but equally silent.

#### [High · High · M] Qdrant payloads go permanently stale on SQLite-only metadata updates — `src/search/index.ts:711`; `src/tools/index.ts:449, 529, 932`; `src/storage/index.ts:219-239`

**Issue:** `QdrantStore.search` filters on the payload fields `tags`, `type`, `decay_eligible` and `expires_at` (`qdrant.ts:305-324`), but four write paths mutate exactly those fields in SQLite only and never re-upsert the point: `recordAccessBatch` on every recall (sliding window rewrites `expires_at`/`retention_tier`), the `tag` tool, `review keep`, and `consolidate merge`'s metadata-only update. `StorageManager.updateMemory` re-upserts the payload only inside `if (newVector)` (`storage/index.ts:220-240`). No repair path exists: `detectAndMarkVectorDrift` compares content checksums only (`558-561`), reconciliation visits only `vector_synced = 0` rows, and `repair --from-qdrant` writes SQLite from Qdrant, never the reverse.

**Failure scenario:** Defaults (`sliding_window_enabled: true`, `tier_ttl.T2: 90`). A T2 memory written on day 0 has `expires_at = day 90` in both stores. Recalls on day 30 and day 60 push SQLite's `expires_at` to day 150; the Qdrant payload still says day 90. On day 91 the `should` clause excludes that point from every semantic query, and `recall` is semantic-only — the most-accessed memory in the store becomes permanently unrecallable while SQLite says it is live and GC will never delete it. Independently, `tag {id, add:['deploy']}` updates SQLite only, so `recall {tags:['deploy']}` pushes `match any ['deploy']` into Qdrant, the point does not match, and the post-filter at `tools/index.ts:256-257` can only remove results, never recover them.

**Why it matters:** An actively-used memory disappears from the primary retrieval path at exactly the moment the sliding window was meant to keep it alive, and tagging a memory makes it unfindable by that tag. `search` in hybrid/fulltext mode still finds these via the FTS leg, which makes the failure look intermittent and nearly undiagnosable.

**Recommendation:** Make the payload a derived artefact of the SQLite row: have `updateMemory` re-upsert with `setPayload` (no vector needed) whenever a `toQdrantPayload`-projected field changes even with no `newVector`, and mark `vector_synced = false` when that call fails so reconciliation replays it. For the high-frequency `recordAccessBatch` path, either drop `expires_at`/`decay_eligible` from the Qdrant filter and apply expiry solely in `buildSearchResults` (which already calls `lifecycle.isExpired`), or batch a periodic payload refresh keyed on `updated_at`.

**Divergence:** SILENT. `vector_synced` stays true, `unsynced_vectors` reports 0, no counter, no log, no health signal while the payload and the row disagree.

#### [High · High · S] `collections.embedding_model` is never updated, so `repair --re-embed` leaves collections write-wedged — `src/storage/index.ts:784-808, 681-758`

**Issue:** `ensureCollectionCompatible` (784-800) rejects any vector-producing write whose active model/dimensions differ from the `collections` row, and `writeMemory` calls it on every write (137). The row is written once by `createCollection` with `INSERT OR IGNORE` (`sqlite.ts:2036-2044`) and `grep -rn "UPDATE collections" src/` returns nothing. `reembedMismatchedVectors` — the remediation the CONFLICT message and the README's migration section both name — re-embeds, re-upserts, re-stamps `memories.embedding_model` and calls `setExpectedEmbeddingIdentity` (755), but never touches the `collections` row.

**Failure scenario:** An operator switches `embedding.model` from `text-embedding-3-small` to `text-embedding-3-large` keeping `dimensions: 1536` — legal per the schema (`config/index.ts:19`) and the only same-dimension change the README covers. Startup degrades embedding health and refuses writes with a CONFLICT naming `repair --re-embed`. The operator runs it; every row re-embeds into the existing 1536-d collection, `converged: true`, health clears. The very next `remember` calls `ensureCollectionCompatible`, finds `col.embedding_model === 'text-embedding-3-small'`, and throws the same CONFLICT naming the command that just completed. Every pre-existing collection is now permanently unwritable; only brand-new collection names work, and `reconcileVectorsFromSqlite` (which calls the same guard per memory at line 611) is wedged identically.

**Why it matters:** The one documented, supported migration path terminates in a permanent write outage with a self-referential remediation message, and there is no tool or CLI command that can update the row — the only escape is hand-editing SQLite. Reads keep working, so the store looks healthy until the next write.

**Recommendation:** Add `SqliteStore.updateCollectionEmbedding(namespace, name, model, dimensions)` and call it from `reembedMismatchedVectors`' convergence branch alongside `setExpectedEmbeddingIdentity` (752-756). Failing that, have `ensureCollectionCompatible` compare against the store's expected embedding identity rather than a per-collection snapshot nothing maintains.

**Divergence:** VISIBLE as a CONFLICT on every write, but misdiagnosed — the error names a remediation that cannot fix it.

#### [High · High · M] Reconciliation aborts the whole run on one failure, and nothing resumes it — `src/storage/index.ts:605-647`

**Issue:** The per-memory catch (638-647) flushes and rethrows, unwinding the entire batch loop, and the whole batch is embedded in one `embedBatch` call (615) so a single non-retryable rejection aborts everything. This is the opposite of the sibling `reembedMismatchedVectors`, whose own docstring (672-675) states failures are isolated "so a single bad row cannot block convergence of the rest of the store". Because `listMemoriesNeedingVectorSync` orders by `created_at ASC, id ASC` (`sqlite.ts:1721`) and the cursor is discarded on the throw, every retry re-encounters the same failing row first. The retry budget is 3 attempts 5 s apart (`backup/index.ts:40-43`) while the breaker's `open_window_ms` defaults to 30,000 — longer than the whole retry span. And no repair mode selects on `vector_synced = 0`: `RepairInputSchema` offers only `from-qdrant` and `re-embed`.

**Failure scenario:** A 50,000-memory backup is restored; 40,000 rows are marked unsynced and background reconciliation starts. Qdrant is restarted 30 s in; five upsert failures open the breaker, the fifth rethrows. Attempts 2 and 3 fire at +5 s and +10 s, both inside the 30 s open window, both failing instantly with `CircuitOpenError` before touching a memory. `retryOrGiveUp` logs `backup_restore_background_reconcile_retries_exhausted` and stops. Qdrant returns 20 s later and nothing retries: `from-qdrant` skips rows already in SQLite, `re-embed` skips rows whose stamp matches, and only another full restore re-triggers reconciliation. A deterministically-incompatible row (F8) head-of-line-blocks the corpus forever; an over-long chunk (F37) does the same.

**Why it matters:** A transient dependency restart — the most common Qdrant event — permanently abandons post-restore reconciliation of an entire corpus, and the documented recovery ("any later reconciliation trigger resumes from the same unsynced set") does not exist as an operator-invocable command.

**Recommendation:** Isolate failures per memory the way `reembedMismatchedVectors` already does (count, log `reconcile_item_failed` with the memory id and collection, advance the cursor, continue) and return a `failed` count in `ReconcileVectorsResult`; on a batch-level embed rejection fall back to per-memory `embed()`. Make the retry backoff exceed `resilience.circuit_breaker.open_window_ms`. Add a repair mode that selects on `vector_synced = 0`.

**Divergence:** VISIBLE that work remains (`unsynced_vectors`, degraded health, an exhausted-retries warn); SILENT that it will never resume and that no command exists to resume it, and no log names the offending memory.

#### [High · High · M] Restore overwrites `brain.db` before proving the image is openable — `src/storage/sqlite.ts:574-582`; `src/backup/index.ts:138-170`

**Issue:** `activateDatabaseImage` closes the live connection, unlinks the WAL/SHM sidecars (`585-597`), `atomicWriteFileSync`s the image onto `brain.db` and calls `openDatabase()` — no try/catch, no snapshot of the outgoing database, no reopen of the previous file on failure. `openDatabase` runs `PRAGMA journal_mode = WAL` immediately, so a body that is not a valid SQLite file throws *after* the rename destroyed the previous `brain.db`. The memory-count cross-check (`backup/index.ts:150-170`) also runs after the swap and, on mismatch, throws over a store that has already been replaced.

**Failure scenario:** Reproduced: activating a non-SQLite buffer throws `file is not a database`, leaves `brain.db` as that garbage, and a fresh `SqliteStore.init()` on the same directory throws identically — the process cannot restart. `restore` accepts an arbitrary caller-supplied absolute path (`tools/index.ts:1079-1080`; the schema declares only `type: string`) and the SHA-256 is self-consistent within the file, so a corrupt-but-consistent artefact passes validation. The ordinary variant needs only a full disk: an `atomicWriteFileSync` failure after `db.close()` leaves `this.db` closed, so every subsequent call throws `database is not open` for the life of the process. And on a header/body count mismatch the operator is told the restore *failed* while their pre-restore database and its WAL sidecars are already gone.

**Why it matters:** Data loss on the one path whose purpose is recovery, presented to the caller as a failed operation — `README.md:2318` promises the call "does not return a successful response", which reads as "nothing changed".

**Recommendation:** Write the image to a scratch path, open and validate it there (`PRAGMA integrity_check`, a `SELECT count(*) FROM memories`) *before* touching `brain.db`; rename the outgoing file aside as `brain.db.pre-restore` rather than overwriting it, and re-activate it if activation or the count check fails. Wrap the whole sequence so a failed write always reopens something. Move the count check ahead of the swap. Separately, derive `memory_count` in `create()` from the exported image rather than a second live query (`backup/index.ts:59-60`), which a concurrent CLI writer can desynchronise.

**Divergence:** VISIBLE as an error and a `backup_restore_activate_failed` log; the *state left behind* is SILENT — nothing tells the operator the old database is gone.

#### [High · High · S] A partial startup hydration is never retried — `src/index.ts:204-215`; `src/storage/index.ts:441-475`

**Issue:** `main()` hydrates a new device only when `sqlite.countMemories() === 0` (205-206). `bootstrapFromQdrant` iterates collections sequentially with no per-collection try/catch — only per-point SQLite failures are isolated — so any Qdrant-side throw mid-loop propagates to `main()`'s catch (213-215), which logs one `bootstrap_error` warn and continues startup. #### [High · High · M] `runGc` materialises every expired memory row, unbounded, on the synchronous SQLite API — `src/backup/retention.ts:61-64`; `src/storage/sqlite.ts:1528-1534`

**Issue:** `listExpiredMemories` is `SELECT * FROM memories WHERE archived = 0 AND decay_eligible = 1 AND expires_at IS NOT NULL AND expires_at < ? The immediately adjacent `listReviewCandidates` takes `limit = 200` and `listMemoriesNeedingVectorSync` is cursor-paginated, so the missing bound reads as an oversight.

**Failure scenario:** A store with 200k–400k T2/T3 memories past `expires_at` — the exact cohort that grows when cleanup has not been running, which per F3 is always. At 02:00 the tick materialises every row through `rowToMemory` into full records at ~1 KB each, i.e. hundreds of MB to low GB of JS heap built synchronously, and the array is then filtered and mapped twice more. Because `DatabaseSync` runs on the event loop, every in-flight HTTP request stalls, `/health` stops responding so an orchestrator's liveness probe kills the container mid-GC, or the process OOMs before the loop starts. The operator sees a restart loop, not a GC problem. The same call is reachable from `gc --dry-run`, where the whole candidate list is additionally serialised into the response.

**Recommendation:** Give `listExpiredMemories` a `limit` and a keyset cursor on `(expires_at, id)`, and have `runGc` loop over bounded pages with a wall-clock budget, yielding to the event loop between pages and reporting `scanned`/`remaining` in `GarbageCollectionResult` so a truncated pass is visible. Select only the columns the archive/delete path needs.

**Deliberate:** `2026-08-30-batch-retention-and-vector-cleanup` batched the deletes and flushes but never bounded candidate selection.

#### [High · High · M] `scrollAll` buffers a whole collection, and distillation then clusters it O(n²) on the event loop — `src/storage/qdrant.ts:554-587`; `src/pipeline/distillation.ts:203`; `src/pipeline/distillation-cluster.ts:57-65`

**Issue:** `scrollAll` pages 100 points at a time but pushes every point into one `allPoints` array with `with_payload: true` and returns only when the scroll is exhausted — no streaming callback, no cap, no field selection. Callers: `bootstrapFromQdrant`, `collectExistingVectorChecksums` (which needs one string field per point), `handleRepair`'s from-qdrant mode, and `DistillationService.findClusters` via `scrollCollection(..., withVector: true)`. The clustering core is an unguarded double loop calling `cosineSimilarity` over full-dimension vectors, and `cosineSimilarity` recomputes each vector's magnitude inside every pair.

**Failure scenario:** 100k memories at 1536 dims with distillation enabled. Memory: ~1.23 GB of JS `number[]` for vectors plus ~150 MB of payload in one array. CPU: even after filtering to ~20,000 T2/T3 episodic candidates, the pair loop is ~2×10⁸ pairs × 1536 multiply-accumulates — tens of minutes of blocked event loop, during which every MCP request, `/health` probe and the shutdown handler are dead. At the 200,000-per-tier budget the design cites as its bound, the run never completes. Restore's checksum pass has the milder version of the same shape: ~1 GB of payloads materialised to read 32 bytes per point, on top of the backup buffer and the database image.

**Recommendation:** (1) Add a streaming form (`scrollEach(name, batchSize, fn)`) and a `payloadFields` passthrough to Qdrant's `with_payload: ['checksum']`, and move `collectExistingVectorChecksums`, `bootstrapFromQdrant` and `handleRepair` onto it so peak memory is one page. (2) Cap candidates per collection in `findClusters` (`retention.distillation.max_candidates_per_collection`) and skip-with-a-warning above it. (3) Precompute L2 norms once and use a dot-product-only inner loop, yielding between outer-loop chunks.

**Deliberate:** `2026-08-30-add-memory-distillation` decision #3 chose one scroll-with-vectors pass over pairwise Qdrant search, arguing "O(n) round trips instead of O(n²)". The trade-off reasoned only about *network* round trips; it bounded n at 200,000 and never checked that the substituted in-memory clustering is O(n²) in CPU and O(n) in resident vectors at that same n.

#### [Medium · High · M] Every memory update and delete does a full FTS5 virtual-table scan — `src/storage/sqlite.ts:1034, 1050, 1082, 2082`

**Issue:** `memories_fts` declares `id` (and `namespace`, `collection`) as `UNINDEXED`, and FTS5 provides no index on an UNINDEXED column, so `DELETE FROM memories_fts WHERE id = ?` cannot seek — `EXPLAIN QUERY PLAN` returns `SCAN memories_fts VIRTUAL TABLE INDEX 0:`. Every write path uses that shape: `updateMemory`'s delete+reinsert, `deleteMemory`, `deleteMemoriesByIds` (one scan per 500-id chunk) and `deleteMemoriesInCollection`.

**Failure scenario:** Measured on the real table shape: ~6.6 ms per delete at 20k rows and ~18.8 ms at 60k, i.e. tens of ms at 100k with content-sized documents. A `forget` of 50 memories on a 100k-memory store stalls the process for seconds, and a `remember` that dedups into an UPDATE stalls tens of ms — synchronously, so pending `/mcp` requests, `/health` and the shutdown handler are all blocked. Cost grows linearly with corpus size, so it degrades silently as the store fills, and no histogram covers SQLite statement latency.

**Recommendation:** Key deletion on something FTS5 can seek: convert `memories_fts` to external-content mode (`content='memories', content_rowid=…`) so deletes are rowid-addressed, or keep an indexed side table mapping `memories.id → memories_fts.rowid`. #### [Medium · High · M] `repair --from-qdrant` buffers whole collections and inserts point-by-point — `src/tools/index.ts:1104-1211`

**Issue:** For each collection it calls `scrollAll` (materialising every point) and then runs a `for (const point of points)` loop containing no `await`: a synchronous `getMemoryById` probe, a `getCollection` lookup on the prepare-per-call path, and an `insertMemory` issuing two separate implicit-transaction statements. **Failure scenario:** A device with an empty SQLite database repairs from a 150k-point Qdrant store over `/mcp`. `scrollAll` holds ~150k payload objects resident, then the loop runs ~150k `getCollection` compilations and ~300k separate implicit transactions with no yield point: the event loop never turns, `/health` does not respond, `/mcp` sessions time out, and the cron timers do not fire — or the payload array alone exhausts the heap and kills the recovery half-finished with no progress record. #### [Medium · High · M] Collectionless recall fans out one full-limit query per collection — `src/storage/qdrant.ts:330-366`

#### [Medium · High · M] Backup creation blocks the event loop and allocates ~3× the database size — `src/storage/sqlite.ts:2196-2210`; `src/backup/index.ts:53-88`

**Failure scenario:** Measured on a synthetic 128 MB store: `VACUUM INTO` 422 ms, `readFileSync` 50 ms, plus hashing, a 127 MB concat and a 127 MB write — roughly a second of hard event-loop stall and ~380 MB of transient buffers. **Recommendation:** Keep `VACUUM INTO` but stop materialising the image: hash and copy the temp file with a stream (`createReadStream` piped through `createHash` into the destination, header written first) so `create()` becomes genuinely async and peak memory is a stream buffer. #### [Medium · High · S] Revision numbers derived from row count collide with `pruneRevisions` — `src/storage/index.ts:204`; `src/storage/sqlite.ts:2128-2139, 315`

**Issue:** `updateMemory` computes the next revision as `this.sqlite.listRevisions(id).length + 1` — a count, not `MAX(revision) + 1`. `pruneRevisions` keeps the *highest* `revisions_per_memory_max` per memory (`ORDER BY revision DESC`, delete where `rn > N`), so after any prune the count is N while the numbers are the top N values, against a `UNIQUE(memory_id, revision)` constraint and a bare `INSERT`.

**Failure scenario:** A T0 memory accumulates revisions 1..21; GC's prune keeps 2..21 (count 20). The next content update computes 21 and hits the constraint. The throw happens at line 204, before `sqlite.updateMemory` at 218, so the update is rejected outright — and recomputes the same colliding number on every retry, so that memory can never be updated again. `revertMemory` routes through the same path. The user sees an opaque `INTERNAL` from `remember` with no mention of revisions.

**Why it matters:** T0 is the tier that exists to hold durable, revisable content, and an on-by-default retention job silently arms a permanent write failure on exactly those memories.

**Recommendation:** Add `SqliteStore.nextRevisionNumber(memoryId)` backed by `SELECT COALESCE(MAX(revision), 0) + 1 …`, or have `insertRevision` compute it in SQL. While there, wrap `insertRevision` + `logAudit` + `updateMemory` in one transaction (see F6).

**Note:** The lead rated this High. It is currently latent — `pruneRevisions`' only caller is `retention.ts:185`, which F3 proves never executes — so it is rated Medium here and escalates to High the moment F3 is fixed. Fix both in the same change.

#### [Medium · High · M] Backup files and `backup_metadata` rows are never pruned — `src/backup/index.ts:53-106`

**Issue:** `create()` writes a full VACUUM'd copy and inserts a metadata row; nothing ever deletes either. `runGc` prunes only the audit log and revisions, there is no `pruneBackups`, no `backup` section in `ConfigSchema` (the only mention of backups in config is the `mkdirSync`), and `list()` returns every historical row with no `existsSync` check. `atomicWriteFileSync` also leaves a `<file>.tmp` behind if the write throws (F24), and `create()`'s catch only rewraps.

#### [Medium · High · S] `search include_archived` returns no archived results when active results fill the limit — `src/tools/index.ts:386-388, 413`

**Issue:** `SearchService.search` appends archived matches after the active list with no re-sort (`search/index.ts:316-319`), and `handleSearch` truncates the concatenation with `filtered.slice(0, input.limit)` after fetching a widened pool. Archived entries sit at positions `>= activeCount`, so they are cut whenever `activeCount >= limit` — the normal case for any non-trivial corpus.

**Failure scenario:** `search({ query: 'deployment', include_archived: true, limit: 10 })` in a namespace with 30+ active matches returns 10 active results and zero archived ones, even though four archived memories matched on summary or tags. The only way to see an archived result is for the namespace to hold fewer than `limit` matching active memories.

**Why it matters:** This contradicts the schema's own comment ("archived matches are appended after active results … and never count against `limit`") and the archived spec requirement that a matching archived memory "SHALL be returned marked as archived". The feature is inert in its intended use — finding something you remember archiving. No test covers the full-limit case.

**Recommendation:** Split `filtered` into active and archived, slice the active half to `input.limit`, and append up to a separate cap of archived entries — mirroring how `handleRecall` appends `follow_links` neighbours after its own slice. Add a handler-level test with a real `SearchService` returning `limit` active results plus an archived match.

**Deliberate:** `2026-08-30-add-review-and-archive-recall` specified the opposite behaviour; this is drift from it, not a trade-off.

#### [Medium · High · S] The `/10` fulltext normaliser saturates at 1.0 for any two-term query — `src/search/index.ts:397, 484`

**Issue:** Both sites clamp with `Math.min(1, Math.abs(rank) / 10)`. `upgrade-fulltext-to-fts5` replaced the old LIKE term-frequency scorer (small integer counts, where `/10` was sane) with `rank = -bm25(memories_fts, 1.0, 2.0, 2.0)` and never revisited the constant.

**Failure scenario:** Measured against a `node:sqlite` FTS5 table using the production tokenizer and column weights over a 500-row corpus: single-term queries yield |bm25| of 9.83 and 8.54 — already near the ceiling; two terms yield 19.66 and 17.07; six terms yield 43.0 and 37.0. All clamp to exactly 1.0. So for `search { mode: 'fulltext', query: 'deploy release' }` every hit reaches `buildSearchResults` with relevance 1.0, `compositeScore` (ranking on by default) multiplies each by `prior × decay`, and the final sort orders results purely by importance, access count and recency. BM25 relevance is discarded entirely and the returned `score`/`fulltext_score` is a constant 1.0 that cannot be thresholded.

**Why it matters:** Fulltext is one of three advertised search modes and its ranking signal is silently destroyed for essentially every real multi-word query. Nothing logs or meters it — the results look plausible, just ordered by the wrong thing.

**Recommendation:** Replace the constant with a scale-free normalisation over the returned candidate set in one shared helper used by both sites — min-max over the batch, or `rank / (rank + k)`. The FTS5 pool is already bounded, so a batch-relative normalisation is cheap. Add a test asserting two fulltext hits with different BM25 ranks keep distinct scores after `compositeScore`. While there, promote the `40` literal at `tools/index.ts:231, 240` to a named constant beside `RRF_K`.

#### [Low · Medium · S] Score comparators lack tiebreakers — `src/search/index.ts:246, 502, 643, 708`

**Issue:** All four sort on score alone. `Array.prototype.sort` is stable, so order is deterministic for a fixed input — but `:246` and `:502` are each immediately followed by a `.slice(...)`, so when two candidates tie exactly at the cut, which one survives is decided by the upstream iteration order, which for the semantic leg is Qdrant's ordering for equal-cosine points — not guaranteed stable across calls or segment merges.

**Failure scenario:** Two memories hold byte-identical content in the same namespace — exactly the state `consolidate` exists to detect — so both come back at the same cosine score. In `hybridSearch` with `limit: 5`, `mergeVariantResults` slices to 10; if the tie straddles position 10 only one is kept, and after a Qdrant segment optimisation the *other* one is kept instead. #### [Low · Medium · S] Rerank sorts LLM `[0,1]` scores against un-reranked composite scores — `src/search/index.ts:630-643`

**Recommendation:** Keep the populations separate — sort the reranked pool by rerank score, sort `rest` by composite score, and return `[...sortedPool, ...sortedRest]` — or map rerank scores back onto the pool's composite range before merging. Add a test asserting an out-of-pool candidate never overtakes a reranked one.

**Deliberate:** `2026-08-30-add-opt-in-rerank-stage` documents the whole-list re-sort as intended and the feature is off by default; it is still a real quality gap when enabled.

The block is discarded without a word, `embedding.provider` keeps its `openai` default, and the server runs — embedding into the wrong vector space and billing the wrong provider, with health reporting everything fine. **Recommendation:** Make `ConfigSchema` and its nested objects `.strict()` so unknown keys fail load with the offending path named — or keep stripping but log a `config_unknown_keys` warning and never write a stripped object over a user-authored file.

#### [Low · High · M] Four god functions, with the payload→record mapping duplicated across three modules — `src/tools/index.ts:481-656, 1084-1233, 204-345`; `src/search/index.ts:407-511`

### Security

#### [High · High · M] Unauthenticated, unrate-limited `/health` runs an uncached 300 s Qdrant probe and answers 200 while degraded — `src/transport/http.ts:205-214`; `src/health/index.ts:154-169`; `src/storage/qdrant.ts:456-479`; `Dockerfile:44-45`

**Issue:** `/health` is registered at line 205, *before* `createAuthMiddleware` (212), `createRateLimitMiddleware` (213) and `createSizeLimitMiddleware` (214), and auth short-circuits it explicitly as well. SQLite aggregates are cached 5 s and the embedding probe 30 s, but `checkQdrant` is uncached and runs on every request; the probe calls `this.client.query(...)` directly rather than through `executeWithBreaker`, and the client has no timeout (F14), so it inherits the 300,000 ms default with undici's own guards disabled. Line 207 returns 200 for both `healthy` and `degraded` — only `unhealthy`, which `computeOverall` raises solely for unhealthy SQLite, yields 503 — and `Dockerfile:45` keys on `r.ok`. The body carries raw exception messages, `counts_by_tier`, `expiring_soon`, `archived_count`, `unsynced_vectors`, `memory_count`, `db_size_bytes`, uptime, distillation totals and breaker states.

**Failure scenario:** (a) The Qdrant host is firewalled to DROP. Every `GET /health` reaches a fetch with a 300-second ceiling and no breaker guard, and there is no auth or rate limit in front, so an unauthenticated caller can hold a very large number of concurrent outstanding fetches and Express responses. (b) Qdrant is simply stopped: `checkQdrant` returns unhealthy, `computeOverall` maps it to `degraded`, the route returns 200, and the Docker/Kubernetes probe reports the container healthy while every `remember` and semantic search fails. (c) `curl http://host:3721/health` against the externally-bound container image returns the full inventory plus which embedding vendor is configured and the raw text of the last Qdrant exception — which can include the internal Qdrant URL — all before the bearer gate.

**Recommendation:** Give `checkQdrant` the same short-TTL cache `checkEmbedding` has and bound the probe (pass `timeout` to the client per F14; keep the breaker bypass deliberate and comment it). Return 503 for `degraded`, or add `/health/ready` and point `Dockerfile:44-45` at it. Split the response into a terse unauthenticated liveness body (`{status, uptime_seconds}`) and keep the full snapshot behind auth on the existing `health://status` resource. Register the rate limiter before `/health`, keeping the auth exemption.

**Deliberate:** `2026-08-30-harden-http-health-rate-limit-and-resource-bounds` and `fix-vector-store-health-fidelity` both reasoned about this endpoint — the latter explicitly accepting that "probe cost is attacker-influenced. A bounded read keeps that acceptable" — but the probe is not bounded, the caching pass skipped it, and the 200-on-degraded/Dockerfile pairing was never revisited.

#### [High · High · S] `ensureDataDir` persists env-injected credentials and security overrides into a world-readable `config.json` — `src/config/index.ts:566-592, 469`

**Issue:** `loadConfig` mutates the parsed config with `applyEnvOverrides` (469) and `ensureDataDir` then serialises *that* object with a plain `writeFileSync` (590) — no temp+rename, no `{ mode: 0o600 }`, so the file lands at the process umask (typically 0644). It fires whenever the file did not exist or `device.id` changed, and both entry points call the pair back-to-back. Everything the overrides touch — `data_dir`, host, port, `qdrant.external_url`, `require_loopback_http`, `allow_unauthenticated_http`, `log_level` — is persisted as if it were a user setting, though AGENTS.md documents these as *runtime overrides*.

**Failure scenario:** A first boot with `BHGBRAIN_QDRANT_URL=https://user:S3cret@cluster.qdrant.io:6333` writes the credential in cleartext at 0644 — readable by any other user or container sharing the volume, and captured by anyone backing the directory up — even though the whole `*_api_key_env` design exists to keep secrets out of that file. Worse: a single debugging run with `BHGBRAIN_ALLOW_UNAUTHENTICATED=true` bakes `"allow_unauthenticated_http": true` into `~/.bhgbrain/config.json`, so every subsequent start *without* that env var still serves `/tool/:name` and `/mcp` with no bearer check, behind one `unauthenticated_http` warn. `BHGBRAIN_REQUIRE_LOOPBACK=false` persists the same way. (The container case is narrower than it looks: `loadConfig` reads the platform default path, not `data_dir`, so a container writing `/data/config.json` never reads it back — the damaging case is the default-path native install.)

**Recommendation:** Snapshot the config *before* `applyEnvOverrides` and persist that, or restrict the first-boot write to what it exists for — `{ device: { id } }` merged onto the raw file contents. Write via a temp+rename helper with `{ mode: 0o600 }` and an fsync (share the writer from F24). If persisting env-derived values is deliberate, log a warning naming each env-sourced key being written, and never write credential-bearing URLs.

**Deliberate:** `2026-08-30-device-namespace-partitioning` D3 addressed the every-startup rewrite; the first-boot write of the env-overridden object was not part of that decision.

#### [High · High · S] The generated bearer token is printed into container logs, and the Qdrant sidecar is published unauthenticated on 0.0.0.0 — `docker-entrypoint.sh:32-39`; `docker-compose.yml:6-7` vs `27-28`; `README.md:145, 165`

**Issue:** `docker-entrypoint.sh:35` echoes `token: ${BHGBRAIN_TOKEN}` to stderr — the Docker log stream — for the auto-generated credential, which stays valid indefinitely because it is re-read from `${DATA_DIR}/bhgbrain-token` on restart. `docker-compose.yml:6-7` binds the app to `127.0.0.1:3721:3721` with an explicit comment about LAN reachability, while `:27-28` publishes the qdrant service as `"6333:6333"` — no interface prefix, so 0.0.0.0 — with no `QDRANT__SERVICE__API_KEY` on the pinned image. `README.md:145` documents the same `-p 6333:6333`.

**Failure scenario:** An operator runs the documented `docker compose --profile self-hosted up`. The BHGBrain API is correctly loopback-only and token-gated; Qdrant is not. Any host on the LAN can `curl http://<host>:6333/collections` and scroll every point in `bhgbrain_global_general`, whose payloads carry the full memory `content` — the entire private corpus the loopback binding was designed to protect — and can DELETE collections, destroying every vector while SQLite keeps the rows. Separately, that operator's bearer token sits in plaintext in `docker logs bhgbrain`, so anyone with container-log read access (a shared CI runner, a log-aggregation index) holds a working credential.

**Recommendation:** `docker-compose.yml:28` → `"127.0.0.1:6333:6333"`, matching line 7, and set `QDRANT__SERVICE__API_KEY` (wired to `qdrant.api_key_env`) if the port must be published; correct `README.md:145/165` to match. In the entrypoint, print only the token *file path* plus a `docker compose exec bhgbrain cat /data/bhgbrain-token` hint, never the value.

**Deliberate:** `2026-08-30-secure-container-default-binding` covers the BHGBrain HTTP port and its bearer token only; the sidecar's published port is never mentioned, so this is an uncovered gap rather than an accepted trade-off.

#### [Medium · High · M] Unbounded rate-limit bucket map, and a boolean `trust_proxy` takes the client-controlled left-most `X-Forwarded-For` — `src/transport/middleware.ts:92-131`; `src/transport/http.ts:194`

**Issue:** `clientBuckets` is an unbounded `Map` keyed on `req.ip`, reclaimed only by an opportunistic sweep at the top of the request handler (at most once per 30 s, deleting only already-expired buckets) — so nothing is reclaimed while traffic is idle, and there is no cap. `security.trust_proxy` is a boolean passed straight to `app.set('trust proxy', …)`; Express's `true` means trust every hop and take the **left-most** XFF entry, which nginx's idiomatic `$proxy_add_x_forwarded_for` leaves client-supplied.

**Failure scenario:** Behind an appending reverse proxy with `trust_proxy: true`, an attacker sends a rotating `X-Forwarded-For: <random IPv4>`. Every request lands in a fresh bucket, so `rate_limit_rpm` is never reached — the limiter is fully bypassed — and the map grows with the distinct-key cardinality of a ~90-second window. The same spoofed value flows into `deriveTrustedClientId` at `http.ts:243`, so `client_id` in every audit row and `tool_call` line is attacker-chosen.

**Recommendation:** Widen `security.trust_proxy` to Express's hop-count/subnet form — the open question `harden-http-auth-and-proxy-trust` left unresolved — so an operator can say `1` and get the right-most-minus-one entry. Independently, give `clientBuckets` a hard `maxEntries`: sweep unconditionally at the cap and, if still over, reject with 429 and log `rate_limit_table_full` rather than inserting, and drive the sweep from an unref'd interval so reclamation does not depend on inbound traffic.

**Deliberate:** `2026-08-30-harden-http-auth-and-proxy-trust` mitigates spoofing by defaulting `trust_proxy` to false and documenting it — a mitigation that assumes a proxy which *replaces* XFF, whereas the common nginx configuration appends.

#### [Low · Medium · S] Data dir, `brain.db`, backups and `config.json` are created at the process umask — `src/config/index.ts:570-590`; `src/storage/sqlite.ts:2534-2538`

**Issue:** `grep -rE 'chmod|mode: 0o' src/` returns nothing across the tree: `mkdirSync(dir, { recursive: true })` for the data dir and `backups/`, bare `writeFileSync` for `config.json`, and no `mode` in `atomicWriteFileSync`. Under the default umask that is 0755 directories and 0644 files.

**Failure scenario:** With a non-default `BHGBRAIN_DATA_DIR` on a shared path (or a distro with a 0755 home), the `.bhgb` archive — an unencrypted, self-contained copy of every memory, the bootstrap profile, company values and the audit log — plus `brain.db` and `config.json` are readable by any other local account. On the default layout `$HOME` at 0750 masks it, which is why this is Low rather than Medium.

**Recommendation:** Create the data dir and `backups/` with `mode: 0o700` and pass `{ mode: 0o600 }` to the config write and to `atomicWriteFileSync`; on non-Windows, `chmodSync` the paths at startup so existing installs are tightened. Document the expectation in the README's Security section.

## 6. Cross-cutting themes

- **The lifecycle lock is the single largest source of defects, in both directions.** It blocks the writes of the job that takes it (F3), it blocks the compensations that exist to make partial dual-store writes visible (F1, F6, F61), and it converts three separate error paths into misattributed messages (F61, F85). One `allowDuringLifecycle` audit across every guarded mutator, plus a pre-flight check before any external mutation, resolves most of it.
- **Compensations are written but not protected.** Every dual-store path has a compensating write; none of them is wrapped in its own try/catch, none passes the lifecycle exemption, and several run in a bare `catch {}` that destroys the original cause. The result is that the mechanism designed to make divergence visible is exactly the mechanism that fails first, so the divergences that do occur are the silent ones.
- **`vector_synced` instruments one direction only.** Everything downstream — `countUnsyncedVectors`, `checkVectorReconciliation`, reconciliation, both repair modes — keys on SQLite rows flagged unsynced. A vector that exists with no SQLite row (F12, F64), a payload that has gone stale (F7), or a row whose flag was never cleared (F1, F2, F6) is structurally invisible. A per-collection point-count-vs-row-count comparison in `HealthService` would close all four.
- **Premises from the sql.js era survive into the native engine.** The single-connection/single-process assumption (F5, F62), the "atomic rename is enough" durability argument (F24), and the crash-visibility claim in the retention comment (F67) were all correct against an in-memory image rewritten wholesale, and none was revisited when the store became a real on-disk file with a second CLI writer.
- **Six near-identical LLM clients, one of which is correct.** `embedding/request.ts` has retry, status classification and breaker-inside-the-classifier; the other six have none of it, in six slightly different ways (F31, F32, F33, F34, F48, F60). This is one shared `chat-client.ts` away from being a non-issue, and the same extraction removes the missing `llm.base_url` capability.
- **Bounds exist everywhere except where the corpus determines the size.** Tool inputs, candidate pools, variant counts and histograms are all explicitly capped; `listExpiredMemories`, `scrollAll`, `markVectorsSyncBatch`, the session registry, the metric maps, the backup directory and the FTS delete scan are not (F13, F16, F17, F22, F25, F30, F55). Every one of them scales with data the operator accumulates rather than with a request parameter, so they degrade silently and fail late.
